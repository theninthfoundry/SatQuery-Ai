## Fixed in this pass

### 1. `apps/web/src/app/api/v1/query/route.ts` — was the worst violation in the repo

This is the single most severe finding. The route did **not** call a
real backend in the common case. It keyword-matched the query text
(`queryLower.includes('sar')`, `.includes('water body')`, etc.) and
returned a fully fabricated analysis: `is_real_weights: true`, fixed
confidence values (0.94–0.98), fixed areas (10.8 ha / 18.45 ha / 26.8 ha
/ 42.15 ha depending on which keywords matched), and a canned
natural-language "answer" string — with **zero** real model inference or
GIS computation, and no real backend call unless `BACKEND_API_URL` was
set *and* reachable. On any failure it silently fell through to the same
fabricated payload. This is exactly the "same UI, different execution
path, different truth standard" danger both source audits describe.

**Fix:** rewritten as a fail-closed proxy. If `BACKEND_API_URL` isn't
configured or isn't reachable, it now returns
`{status: "unavailable", data_class: "UNAVAILABLE_CAPABILITY", ...}`
with HTTP 503/502 — never a fabricated result. Original preserved as
`route.ts.ORIGINAL_FABRICATED.bak` alongside the new file.

### 2. `apps/web/src/app/api/v1/analysis/grounding/route.ts`

Always returned the identical hardcoded feature ("Primary River Channel
& Water Basin", 421,500 m², confidence 0.96, a fixed Brahmaputra
polygon) for **every** request regardless of `image_id` or
`referring_expression`. Fixed the same way: proxy or fail closed with
`boxes: []` / `confidence: null` / `fallback_used: true`, matching the
project's own `backend/agent/grounding_contract.py` fail-closed contract.

### 3. `apps/web/src/app/api/v1/analysis/change/route.ts`

Always returned the identical two hardcoded change clusters (8.2 ha +
10.25 ha, `is_trained: true`, "converged at 95.2% F1 score") regardless
of which images were compared. Fixed the same way; on fallback now
labels the result `classical_rgb_change_fallback` per
`backend/agent/change_contract.py`, never attributes it to ChangeNet.

### 4. `apps/web/src/context/WorkspaceContext.tsx` — partial fix

This file is 1,972 lines and is where the bulk of the remaining 429
violations live. Three concrete things were fixed:

- **The literal initial React state was fabricated data.** `clusters`,
  `findings`, and `evidenceLayers` were initialized via
  `useState(DEFAULT_CLUSTERS)` / `useState(DEFAULT_FINDINGS)` /
  `useState(DEFAULT_EVIDENCE_LAYERS)` — constants containing a fake
  "ChangeNet, 94.2% confidence, `realWeights: true`,
  checkpoint `changenet_s2_weights_val_iou_0.842.pt`" result. Every
  session opened already "showing" this fabricated finding, before any
  query ran.
- **`setFindings` was never called anywhere else in the file.** Grep
  confirms it: the Findings/Evidence panel was **permanently** stuck on
  this fabricated content no matter what a real query returned. This is
  a functional bug, not just a bad default.
- **Fix applied:** the three constants are renamed to
  `GOLDEN_MISSION_FIXTURE_CLUSTERS` / `_FINDINGS` / `_EVIDENCE_LAYERS`
  (they are legitimately the Golden Mission benchmark-tolerance spec —
  see `lib/goldenMission.ts` — just mislabeled as live defaults). All
  three pieces of state now start **empty**, and a new `useEffect` loads
  the fixtures **only** when `workstationMode === 'SCIENTIFIC
  BENCHMARK'` (a mode the UI already exposes but which was previously
  disconnected from the actual data shown), and clears them when the
  user switches to `'LIVE EARTH'`. `selectEvidenceLayer` was also fixed
  — it was looking up the static fixture array regardless of mode; it
  now looks up the live `evidenceLayers` state.

Original preserved as `WorkspaceContext.tsx.ORIGINAL_FABRICATED.bak`.
Syntax-checked with `tsc --noEmit` (no `node_modules` in this
environment, so type-checking against the project's own dependencies
wasn't possible — only structural/syntax validation was) — no errors
introduced.

**Not fixed (see "Still open" below):** the live-query response handler
in this same file (~line 1477–1497 in the original) pads missing backend
response fields with the *same* fabricated numbers (`?? 0.94`, `|| 2.56`,
`: 12.4`, etc.), meaning genuine backend results still get contaminated
with fake values whenever a field is absent. And `setFindings` is still
never wired into the real query-completion handler — the Findings panel
still won't update from a real result until that's added.

## Still open — prioritized, with exact locations

### P0 — Live-result contamination in `WorkspaceContext.tsx`

Search the file for `setCorroborationMetrics` (~line 1470 post-edit).
The handler that processes a *real* backend response does this:

```ts
const tempScore = Math.round(((confObj?.model_score ?? factors?.model_confidence ?? factors?.temporal_changenet ?? 0.94) as number) * 100);
const optScore  = Math.round(((confObj?.resolution_score ?? factors?.optical_quality ?? factors?.optical_reflectance ?? 0.88) as number) * 100);
const sarScore  = Math.round(((confObj?.sar_agreement_score ?? factors?.sar_agreement ?? factors?.sar_corroboration ?? 0.91) as number) * 100);
const regScore  = Math.round(((confObj?.registration_score ?? factors?.registration_quality ?? factors?.registration ?? 0.96) as number) * 100);
const impactVal = pipeRes?.change_percent !== undefined ? Number(pipeRes.change_percent) : (... ?? 12.4);
```

Every `??`/`:` fallback here is one of the exact fabricated Golden
Mission numbers. If the real backend's response is missing any of these
fields, the UI silently displays a fake score instead of an honest
"not reported" state. **Fix pattern:** change each fallback to `null`,
and update the consuming UI (`corroborationMetrics` display components —
not yet located/audited) to render "—" or omit the bar rather than a
number, matching the `EvidenceFactors` pattern already established in
`backend/evidence/contract.py` (`Optional[float] = None` throughout, no
defaults).

Similarly `setFindings` needs to be called in this same success path —
right now only `setClusters(newClusters)` runs; build an analogous
`dynamicFinding` (the code already partially does this — see
`createCanonicalFinding` call a few lines below `setClusters`) and call
`setFindings([dynamicFinding, ...])` / `setActiveFinding(dynamicFinding)`
so the Findings panel actually reflects live results.

## What this pass did *not* attempt, and why

- **No changes to `_archive/`** — the repo already quarantines legacy
  code there per the audits' own recommendation; out of scope.
- **No changes inside React components/drawers beyond `WorkspaceContext.tsx`**
  — this environment has no `node_modules`, no dev server, and no way to
  visually verify a Next.js app. Editing 12–16-violation files blind,
  without the ability to run or screenshot the result, risks shipping
  breakage the next person can't easily catch. The route.ts fixes and
  the `WorkspaceContext.tsx` state-initialization fix were judged safe
  enough to make blind (isolated units / additive-then-syntax-checked
  changes); deeper component edits were not.
- **No training, no model downloads, no GPU work** — unchanged from
  earlier passes in this conversation; still needs your machine.
